assess — User Manual

Perform the DCMA 14-Point Schedule Assessment on a Microsoft Project export (Excel or CSV) and produce terminal, HTML, CSV, and Excel exception reports.

schedulegate v1.0.6 · DCMA PAM Rev. B · August 2026

📋Overview

The assess command reads a schedule file and computes up to 14 health metrics defined by the Defense Contract Management Agency (DCMA) Program Assessment and Reporting Manual (PAM). Each metric produces a pass/fail verdict, a percentage value, and — where applicable — a per-task exceptions list you can export to Excel for corrective action.

The tool supports Excel (.xlsx) and CSV schedule exports. Column headers are matched case-insensitively with fuzzy alias resolution so most Microsoft Project default layouts work without pre-processing.

Scope of assessment: Summary tasks and milestones are excluded from most metric denominators. The tool operates only on work (leaf) tasks unless the metric explicitly involves milestones (e.g. CPLI).
Task ID resolution: MS Project exports often contain both a Task ID / ID column (the sequential row number users see in the left-hand column) and a Unique ID column (a permanent internal identifier). When both are present the tool always uses Task ID, so every value in the exceptions report maps directly to the row number visible in the source schedule. Unique ID is used only as a fallback when no primary Task ID column exists.

⚡Quick Start

Minimum viable usage — run all 14 metrics and print to terminal:

$ schedulegate assess my_schedule.xlsx

Full-featured run with all output formats:

$ schedulegate assess my_schedule.xlsx \
  --customer "Acme Corp" --project "P-1042" \
  --status-date 05/19/2026 \
  --html report.html \
  --csv database.csv \
  --exceptions-report exceptions.xlsx \
  --date-locale US --pct-format 0-100 \
  --verbose

Run only specific metrics (e.g. Logic, Lags, and BEI):

$ schedulegate assess schedule.xlsx --metrics 1,3,14

🚩Command Flags

file
Path to the schedule file to assess. Accepts .xlsx (Microsoft Project Excel export) or .csv. Positional argument — must be the first argument after assess. Required.
Required
-m, --metrics
Comma-separated list of metric IDs to run (integers 1–14). When omitted, all 14 metrics are executed. Example: --metrics 1,5,12  ·   Run only Logic, Hard Constraints, and Critical Path Test.
Optional
--status-date
Override the schedule's status (data) date used for date-dependent metrics (Invalid Dates, Missed Tasks, BEI, CPLI). Defaults to today's date when not supplied. Accepted formats: YYYY-MM-DD · MM/DD/YYYY · MM-DD-YYYY · MM/DD/YY · MM-DD-YY
Optional
--customer
Customer name embedded in the HTML and CSV reports. Does not affect metric calculations. Example: --customer "Lockheed Martin"
Optional
--project
Project number or identifier embedded in reports. Does not affect metric calculations. Example: --project "N00019-24-C-1234"
Optional
--html
File path for the HTML assessment report. The file is created (or overwritten) and automatically opened in the default browser after generation. Example: --html ./reports/assessment.html
Output
--csv
File path for a CSV database file. Results are appended (not overwritten), making this suitable for tracking assessments across multiple schedule versions over time. Optimised for Power BI ingestion. Example: --csv ./db/history.csv
Output
--exceptions-report
File path for an Excel workbook (.xlsx) listing every task that triggered a metric violation, along with a plain-English corrective action for the PM. One sheet per metric. Example: --exceptions-report exceptions.xlsx
Output
--pct-format
Override the percent complete scale used when reading the schedule file. MS Project exports percent complete as 0–100. Primavera and some other tools use 0.0–1.0 (fraction). Accepted values: "0-100" (default) · "fraction" (auto-multiplies by 100)
Optional
--date-locale
Controls which date format is tried first when the reader encounters an ambiguous datetime string. Affects Start, Finish, and all baseline and actual date columns. Accepted values: "US" (MM/DD/YYYY first, default) · "EU" (DD/MM/YYYY first)
Optional
--debug-logic
Prints a per-task successor resolution trace during Metric 1 (Logic) assessment. Shows which tasks have successors inferred from other tasks' predecessor strings, and which are missing successors. Useful when auditing Metric 1 results or troubleshooting unexpected missing-logic percentages.
Optional
-v, --verbose
Appends raw numerator / denominator counts to each metric row in the terminal output. Useful for auditing and troubleshooting unexpected results. Example output: Logic  3.2%  [7 / 219]
Optional

📤Output Formats

🖥️
Terminal
Always produced. Shows the ASCII logo, overall score card, and a colour-coded pass/fail row per metric. Add --verbose for raw counts.
🌐
HTML Report
Dark-theme interactive report with score gauge, metric results, and expandable exceptions table. Auto-opens in browser. Triggered by --html.
📊
CSV Database
One row per assessment run appended to a flat file. Designed for trend analysis and Power BI dashboards. Triggered by --csv.
📁
Excel Exceptions
Multi-sheet Excel workbook. Each failing metric gets its own sheet listing offending Task IDs, names, and corrective guidance. Triggered by --exceptions-report. Task IDs shown always match the Task ID / ID column from the source schedule (the sequential row number visible in MS Project's left-hand column), so flagged tasks can be located directly without any ID translation.

🔍Audit Reference

Purpose: This section documents every convention the tool uses so that auditors can reproduce any result independently from raw schedule data.
Overall Score Formula

The overall score shown at the top of the report is simply:

Overall Score = metrics that PASS ÷ metrics that ran (excluding N/A)

A metric is excluded from the denominator only when it returns N/A (currently only Metric 10 — Resources, when no resource column is present in the export). Binary metrics (Metric 12) count as 1 pass or 1 fail, never fractional.

"Work Task" — Population Definition

Most metrics operate on the work task population, defined as tasks where all of the following hold:

  • IsSummary = false — roll-up summary rows are excluded
  • IsMilestone = false — zero-duration milestones are excluded

Metrics that additionally restrict to incomplete tasks further require PercentComplete < 100. The one exception is Metric 5 (Hard Constraints), whose population includes milestones but excludes summary tasks, because a hard-constrained milestone is a genuine network violation.

Summary rows: always excluded Milestones: excluded from most metrics Milestones: included in Metric 5 only Milestones: included in CPLI completion search (Metric 13)
Predecessor String Parsing (Metrics 1–4)

The Predecessors column is a delimited string of one or more relationship tokens. The tool splits on commas (,) and semicolons (;) then parses each token with the grammar:

token = <TaskID> [ <RelType> ] [ sign <magnitude> <unit> ]
RelType = FS | SS | FF | SF (default: FS if omitted)
sign = + (positive lag) | - (negative lag / lead)
unit = d (days) | w (weeks)
Token example Interpretation Affects
5 Task 5, FS, no lag — compliant Metric 1, 4
5FS Task 5, Finish-to-Start — compliant Metric 1, 4
5SS Task 5, Start-to-Start — non-FS violation Metric 4
5FS+3d Task 5, FS, +3 day lag violation Metric 3
5FS-3d Task 5, FS, –3 day lead violation Metric 2
Schedule Field Units & Data Types
Field Unit / Type Used by Metric(s)
TotalSlack Decimal working days (float) 6, 7, 12, 13
BaselineDuration Decimal working days (float) 8
PercentComplete 0–100 (numeric) 1–11, 14
Start / Finish Forecast dates 9, 13
ActualStart / ActualFinish Actuals dates (nil = not yet set) 9
BaselineFinish Date (nil = no baseline) 11, 14
ConstraintType String (case-insensitive) 5

📐DCMA 14-Point Metrics

Transparency note: Every metric below documents exactly what population is selected, which field drives the calculation, the formula used, and the DCMA PAM reference. This section is intended to be shared with PMs so they understand precisely why a task was flagged.
1
Logic PAM § 4.1 — Network Logic
≤ 5% ▾

Measures whether every incomplete work task is wired into the network — i.e., has at least one incoming (predecessor) and one outgoing (successor) logic link.

What it measures

The percentage of incomplete non-summary, non-milestone tasks that are missing a predecessor, a successor, or both.

Population

All tasks where IsSummary = false, IsMilestone = false, and PercentComplete < 100.

Formula
tasks missing pred or succ ÷ total incomplete tasks

Successor presence is inferred: a task is considered to have a successor if its Task ID appears in any other task's Predecessors field.

Threshold & direction

Pass when result ≤ 5 %. Lower is better.

Exception conditions
No predecessor or successor (island) Missing predecessor only Missing successor only

Corrective guidance in exceptions report: add Finish-to-Start logic links to fill gaps.

2
Leads PAM § 4.2 — Leads (Negative Lag)
0% ▾

Negative lag (a "lead") allows a successor to start before its predecessor finishes. DCMA treats this as artificial schedule compression that hides true logic; the PAM goal is zero.

What it measures

The percentage of predecessor relationships on incomplete tasks that carry a negative lag value.

Population

All individual predecessor links on incomplete, non-summary, non-milestone tasks. Denominator is relationships, not tasks.

Formula
links with negative lag ÷ total predecessor links

A predecessor token like 5FS-3d indicates a 3-day lead and is counted as a violation.

Threshold & direction

Pass when result equals 0% (zero tolerance).

3
Lags PAM § 4.3 — Lags (Positive Lag)
≤ 10% ▾

Positive lags introduce waiting time between a predecessor and successor without an explicit task representing that work. DCMA requires any delay to be modelled as a real task so it can be tracked and resourced.

What it measures

The percentage of predecessor relationships on incomplete tasks that carry a positive lag value.

Population

Same as Leads: individual predecessor links on incomplete work tasks.

Formula
links with positive lag ÷ total predecessor links

Token like 22FS+5d counts as a lag violation.

Threshold & direction

Pass when result ≤ 10 %. Insert an intermediate task to model the delay instead.

4
Relationship Types PAM § 4.4 — FS Relationships
≥ 90% ▾

Finish-to-Start (FS) is the only relationship type that models true sequential work. SS, FF, and SF relationships often mask schedule compression or insufficient decomposition.

What it measures

The proportion of all predecessor links on incomplete work tasks that use the Finish-to-Start relationship type.

Population

All predecessor links on incomplete work tasks. Links with no explicit type token are assumed to be FS (MS Project default).

Formula
FS links ÷ total links

A token like 5SS is a non-FS violation. A bare 5 defaults to FS and counts as compliant.

Threshold & direction

Pass when result ≥ 90 %. Higher is better; 100 % is ideal.

5
Hard Constraints PAM § 4.5 — Constraints
≤ 5% ▾

Hard constraints lock a task to a specific date, overriding network-driven scheduling. They inflate float values and prevent the critical path from being computed correctly.

What it measures

The percentage of incomplete tasks (including milestones but excluding summary tasks) that carry a hard constraint type.

Hard constraint types detected
Must Finish On (MFO) Must Start On (MSO) Start No Later Than (SNLT) Finish No Later Than (FNLT)
Formula
tasks with hard constraint ÷ total incomplete tasks
Threshold & direction

Pass when result ≤ 5 %. Replace with ASAP or Start No Earlier Than (SNET) where possible.

6
High Float PAM § 4.6 — High Float
≤ 5% ▾

Excessive total float (slack) indicates a task is poorly connected to the rest of the network — usually caused by missing successor links, hard constraints, or an unrealistically late project finish milestone.

What it measures

The percentage of incomplete work tasks whose Total Slack field exceeds the 44-working-day threshold.

Threshold value

44 working days (~2 calendar months). Tasks with TotalSlack > 44 are flagged.

Formula
tasks with TotalSlack > 44 ÷ total incomplete work tasks
Threshold & direction

Pass when result ≤ 5 %. Lower is better.

7
Negative Float PAM § 4.7 — Negative Float
≤ 5% ▾

Negative float means a task is already late relative to its constraint or project finish date. It typically signals a hard constraint, an overly compressed logic path, or an unrealistic baseline.

What it measures

The percentage of incomplete work tasks with a TotalSlack < 0.

Root causes
  • Hard constraint (MFO/MSO/FNLT/SNLT) overriding logic
  • Task duration longer than available time window
  • Predecessor chain longer than expected finish
Formula
tasks with TotalSlack < 0 ÷ total incomplete work tasks
Threshold & direction

Pass when result ≤ 5 %. Zero is ideal.

8
High Duration PAM § 4.8 — Duration
≤ 10% ▾

Long work packages are harder to track, resource, and recover when they slip. DCMA requires work packages to be decomposed so no single task exceeds three months (60 working days).

What it measures

The percentage of incomplete work tasks whose Baseline Duration exceeds 60 working days.

Field used

BaselineDuration (working days). Uses the baseline, not the current duration, to detect over-long original plans.

Formula
tasks with BaselineDuration > 60 ÷ total incomplete work tasks
Threshold & direction

Pass when result ≤ 10 %. Break violating tasks into sub-tasks of ≤ 60 working days.

9
Invalid Dates PAM § 4.9 — Invalid Dates
≤ 5% ▾

Dates that are inconsistent with the status (data) date indicate a stale schedule or incorrect actuals. Any incomplete task with forecast dates in the past, or actual dates in the future, is flagged.

Conditions checked
Forecast Start before status date Forecast Finish before status date Actual Start after status date Actual Finish after status date
Population

Incomplete work tasks only (PercentComplete < 100, non-summary, non-milestone). The status date defaults to today unless overridden via --status-date.

Formula
tasks with any invalid date ÷ total incomplete work tasks
Threshold & direction

Pass when result ≤ 5 %. Use --status-date to align to the schedule's actual data date if the default (today) is incorrect.

Tip: If you export a schedule that was last updated weeks ago, set --status-date to the schedule's actual data date to avoid false positives on this metric.
10
Resources PAM § 4.10 — Resource Loading
≥ 95% ▾

Resource-loading a schedule is required to support earned value analysis and cost performance tracking. Unresourced tasks cannot yield reliable BCWS/BCWP values.

What it measures

The percentage of incomplete work tasks that have at least one resource assigned in the Resources column.

N/A handling

If no task in the entire schedule has a resource assigned, the metric is marked N/A and excluded from the pass/fail tally. This handles schedules exported without resource columns.

Formula
tasks with at least 1 resource ÷ total incomplete work tasks
Threshold & direction

Pass when result ≥ 95 %. Higher is better.

11
Missed Tasks PAM § 4.11 — Schedule Adherence
≤ 5% ▾

A task is "missed" when its baseline finish date has passed but it is not yet 100% complete. High missed-task rates indicate a schedule that is no longer representative of actual progress.

What it measures

The percentage of work tasks whose BaselineFinish ≤ StatusDate that are still incomplete (PercentComplete < 100).

Population

Only tasks that were due by the status date (BaselineFinish ≤ StatusDate) are included in the denominator. Tasks with no baseline finish are excluded.

Formula
past-due incomplete tasks ÷ all tasks due by status date
Threshold & direction

Pass when result ≤ 5 %. Corrective action: update actual progress or revise the baseline.

12
Critical Path Test PAM § 4.12 — Critical Path Validity
Pass / Fail ▾

A valid critical path must exist: at least one work task must have zero or negative total float, confirming the scheduler is driving the finish date through network logic rather than hard constraints.

What it measures

Binary test: does any non-summary, non-milestone work task have TotalSlack ≤ 0? Yes = Pass, No = Fail.

Why summary tasks and milestones are excluded

Summary task TotalSlack values are roll-ups derived from child tasks, not independent network-driven float. Milestone float can be zero trivially by constraint. Using either would produce false positives.

Formula
COUNT(work tasks where TotalSlack ≤ 0) > 0

Population = IsSummary = false AND IsMilestone = false. If count > 0 → Pass (value = 1.0). If count = 0 → Fail (value = 0.0).

Threshold & direction

Pass when at least one critical work task exists. No per-task exceptions are generated — the test is schedule-level. The Details field exposes the raw critical_tasks count for transparency.

13
Critical Path Length Index (CPLI) PAM § 3.1.2.3 — Schedule Efficiency
≥ 1.0 ▾

CPLI quantifies schedule efficiency relative to the critical path. A value below 1.0 signals the project is behind schedule and cannot finish on time under current conditions. A value above 1.0 indicates schedule margin.

What it measures

The ratio of "available time plus total float" to the remaining critical path duration. A schedule-level index, not task-level.

Completion task selection

The tool scans all non-summary tasks (milestones included) that have a non-nil forecast finish date and selects the one with the latest Finish. That task provides both the project end date and the TotalSlack used in the formula.

Step-by-step calculation (reproducible)
Step 1 — find completion task:
  completionTask = task with max(Finish) where IsSummary = false

Step 2 — remaining calendar days:
  calDays = (completionTask.Finish − StatusDate) in whole days

Step 3 — convert to working days (5-day week, no holiday calendar):
  CPL = calDays × (5 ÷ 7)

Step 4 — total float from completion task:
  TF = completionTask.TotalSlack (working days, can be negative)

Step 5 — index:
  CPLI = (CPL + TF) ÷ CPL

If CPL ≤ 0 (status date is at or past the project finish), CPLI returns 1.0 / Pass automatically — the schedule has no remaining critical path to measure. No per-task exceptions are produced; the Details field exposes raw cpl and tf values for independent verification.

Interpretation: CPLI = 1.0 means exactly on time. CPLI > 1.0 means margin exists (positive TF). CPLI < 1.0 means recovery is required. A value of 0.95, for example, means the schedule needs to be executed 5 % faster than planned to hit the current finish date.
14
Baseline Execution Index (BEI) DCMA BEI — Schedule Execution
≥ 95% ▾

BEI measures how many tasks were actually completed relative to how many were planned to be complete by the status date. It is a leading indicator of schedule execution health and correlates with CPI/SPI in earned value analysis.

What it measures

The ratio of completed work tasks to all work tasks whose baseline finish was on or before the status date.

Population (both variables)

Work tasks only (IsSummary = false, IsMilestone = false). Tasks with a null BaselineFinish are excluded from the denominator but are still counted in the numerator if complete.

Exact formula & variable definitions
Numerator = COUNT(work tasks where PercentComplete = 100)
              [ALL completed work tasks, regardless of whether they had a baseline]

Denominator = COUNT(work tasks where BaselineFinish ≤ StatusDate
                      AND BaselineFinish ≠ null)

BEI = Numerator ÷ Denominator

Auditor note — why BEI can exceed 1.0: Because the numerator counts all completed tasks (including those that finished ahead of their baseline), while the denominator counts only tasks due by the status date, BEI will be > 1.0 when a significant number of tasks completed early. This is intentional — early completion is rewarded as positive execution performance. Conversely, if many tasks were completed but none had baselined finish dates on or before the status date, the denominator approaches zero and BEI is returned as 1.0 / Pass (no exceptions).

Edge case: If Denominator = 0 (no tasks have a baseline finish on or before the status date — schedule is entirely future-dated or has no baseline), BEI returns 1.0 / Pass with zero exceptions. No assessment is possible without historical baseline data.
Corrective action when BEI < 0.95: Each incomplete task in the exceptions report was planned to finish before the status date. Record actual progress or re-baseline tasks that have genuinely been descoped. The Details field exposes completed, baseline_count, and missing_baseline counts for full traceability.
